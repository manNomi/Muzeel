# WebMCP를 활용한 Muzeel 확장 연구 방향

## 현재 생각하고 있는 문제

원본 Muzeel은 페이지의 DOM 요소와 이벤트 리스너를 찾아 상호작용을 실행한다.
이 방식은 버튼을 누른 뒤 나타나는 모달이나 입력 결과에 따라 달라지는 화면을
충분히 탐색하지 못할 수 있다. 이때 탐색되지 않은 경로에서 필요한 함수가
사용되지 않은 함수로 잘못 분류될 수 있다.

초기에는 AI Agent가 페이지의 상태와 행동을 그래프로 만드는 WebMap을 생각했다.
하지만 동적인 화면을 상태와 행동의 그래프로 표현하는 방법과 그래프를 Agent의
탐색에 사용하는 방법은 이미 여러 연구에서 다뤄졌다. 따라서 WebMap을 만드는
것만으로는 연구의 차이를 설명하기 어렵다.

현재는 WebMCP가 제공하는 행동의 의미와 브라우저에서 실제로 확인한 실행 결과를
연결하는 방향을 검토하고 있다.

## WebMCP를 사용하는 이유

DOM 기반 Agent는 버튼의 글자와 위치 및 주변 요소를 보고 버튼의 목적을
추측한다. WebMCP를 적용한 페이지는 검색이나 필터 적용과 같은 기능을 이름과
설명 및 입력 형식이 있는 도구로 제공할 수 있다.

예를 들어 DOM에서는 같은 모양의 버튼 두 개로 보이더라도 WebMCP에서는 다음과
같이 기능의 목적을 구분할 수 있다.

```text
search_university(country, language_test)
open_login_dialog()
change_home_university(university_id)
```

WebMCP는 2026년 9월 현재 확정된 W3C 표준이 아니다. W3C Web Machine Learning
Community Group에서 작성 중인 초안이며 Chrome에서도 실험 기능으로 제공되고
있다. 연구에서는 WebMCP를 완성된 표준이 아니라 의미 기반 웹 인터페이스의 한
사례로 다룬다.

## 좁힌 연구 방향

Agent가 수행한 행동 하나를 다음 정보와 함께 기록한다.

```text
행동 전 상태
→ WebMCP 도구 또는 DOM 행동
→ 행동 후 상태
→ 새 네트워크 요청
→ 새 JavaScript chunk
→ 새로 실행된 함수
→ JavaScript 처리 시간
```

이 기록을 모아 상태와 행동 및 JavaScript 코드 사이의 관계를 만든다. 이 문서에서는
이를 임시로 `state-action-code map`이라고 부른다.

WebMCP의 도구 설명만으로 실제 동작을 판단하지 않는다. 행동 전후의 화면과
네트워크 요청 및 함수 실행 기록을 함께 확인한다. 선언된 기능과 실제 결과가
다르면 그 차이도 실험 데이터로 남긴다.

## 기존 Muzeel과의 차이

| 구분 | 원본 Muzeel | 검토 중인 방향 |
| --- | --- | --- |
| 행동 선택 | DOM과 이벤트 리스너 기반 | WebMCP 의미 정보와 DOM 보완 탐색 |
| 상태 확인 | 이벤트 실행 중심 | 행동 전후 상태를 각각 기록 |
| 코드 연결 | 실행된 함수 기록 | 상태와 행동별 함수 및 chunk 기록 |
| 최적화 | 관찰되지 않은 함수 본문 제거 | 예상 경로의 코드를 먼저 준비하고 나머지는 지연 |
| 예측 실패 | 제거한 기능이 손상될 수 있음 | 원본 코드로 다시 처리하는 보수적 복구 |

가장 중요한 차이는 코드를 바로 삭제하지 않는다는 점이다. 한 번의 탐색에서
실행되지 않은 함수는 실제 dead code가 아니라 이번 실행에서 관찰되지 않은
함수일 수 있다.

## 노벨티 후보

현재 가장 가능성이 있다고 보는 차이는 다음과 같다.

### 1. 의미 기반 행동과 JavaScript 실행 정보의 연결

기존의 Web Agent 연구는 상태 그래프를 주로 탐색과 작업 성공률 개선에 사용한다.
이 연구에서는 각 상태 전이에 실제로 필요한 JavaScript chunk와 함수를 연결해
브라우저 처리 비용을 줄이는 데 사용한다.

### 2. WebMCP 선언의 실제 동작 확인

WebMCP 도구의 설명이 실제 동작과 일치하는지 확인하고 WebMCP에 빠진 화면
상호작용을 DOM 탐색으로 찾는다. 페이지가 제공한 의미 정보를 그대로 신뢰하지
않고 실제 브라우저 실행으로 확인한다.

### 3. 기능을 삭제하지 않는 재방문 최적화

이전 방문에서 자주 사용됐다는 이유만으로 다른 코드를 삭제하지 않는다. Agent가
예상한 다음 경로에 필요한 코드를 먼저 로드하거나 컴파일하고 나머지는 늦춘다.
예측하지 못한 행동이 발생하면 원본 코드를 사용한다.

이 세 항목을 각각 새로운 기술이라고 주장할 수 있는지는 아직 확인이 더 필요하다.
특히 V8 code cache와 lazy compilation 및 기존 profile 기반 code splitting 연구와
겹치는 범위를 추가로 확인해야 한다.

## 연구 질문 후보

현재는 다음 질문을 우선 검토하고 있다.

> WebMCP가 제공하는 의미 기반 행동과 실제 JavaScript 실행 정보를 연결하면
> 기능 손상 없이 웹 애플리케이션의 탐색 범위와 재방문 성능을 개선할 수 있는가?

세부 질문은 다음과 같다.

- 같은 시간과 행동 횟수에서 WebMCP와 DOM을 함께 사용하는 Agent가 원본
  Muzeel보다 더 많은 상태와 실행 경로를 발견하는가?
- 각 상태 전이에 필요한 JavaScript chunk와 함수를 얼마나 정확하게 연결할 수
  있는가?
- 이 관계를 사용했을 때 이미 HTTP cache와 V8 code cache가 적용된 재방문에서도
  추가적인 성능 개선이 있는가?
- 탐색에 사용하지 않은 사용자 행동에서도 기능이 유지되는가?
- WebMCP에 선언되지 않은 기능이나 잘못 설명된 기능을 DOM 보완 탐색으로 찾을 수
  있는가?

## 비교 방법

다음 네 가지 방법에 같은 시간과 행동 횟수를 적용한다.

1. 원본 Muzeel 탐색
2. 정해진 순서로 새 요소를 실행하는 규칙 기반 탐색
3. DOM 정보를 읽는 AI Agent 탐색
4. WebMCP와 DOM을 함께 사용하는 AI Agent 탐색

탐색 결과는 다음 기준으로 비교한다.

- 발견한 상태와 행동 수
- 실행에 성공한 상태 전이 수
- 발견한 JavaScript chunk와 함수 수
- 새 상태 하나를 찾는 데 사용한 행동 수와 시간
- 탐색에 사용하지 않은 기능 시나리오의 성공률
- 재방문의 JavaScript 전송량과 파싱 및 컴파일 시간
- 예측 실패로 원본 코드를 다시 사용한 횟수

## Solid Connection 적용 계획

기존 실험은 로그인 전 홈 화면의 고정된 스냅샷에서 진행했다. AI Agent가 선택한
12개 행동으로 JavaScript 감소 후보를 만들고 별도로 분리한 다섯 개의 회귀
시나리오를 실행했다. 이 결과는
[`solid-connection-agent-run-20260814-ko.md`](solid-connection-agent-run-20260814-ko.md)에
정리되어 있다.

다음 실험에서는 Solid Connection을 수정하지 않고 공개 화면을 읽기 전용으로
사용한다. 행동이 끝날 때마다 새 요소와 네트워크 요청을 다시 확인한다. 이
실험은 기존 결과를 다시 실행한 것이 아니며 아직 계획 단계다.

예상 순서는 다음과 같다.

1. 홈 화면에서 WebMCP로 제공할 수 있는 기능 후보를 정리한다.
2. 원본 Muzeel과 DOM Agent 및 WebMCP 보완 Agent의 행동 범위를 고정한다.
3. 행동 전후의 상태와 동적 chunk 및 함수 실행 기록을 수집한다.
4. 탐색에 사용하지 않은 별도 기능 시나리오를 정한다.
5. 기능 보존이 확인된 경우에만 재방문 최적화 실험을 진행한다.

## 현재 단계와 다음 할 일

현재는 논문 주제가 확정된 단계가 아니다. WebMap 자체를 연구 결과로 삼기보다
WebMCP의 의미 정보와 실제 JavaScript 실행 정보를 연결하는 질문으로 범위를
좁히고 있다.

다음 할 일은 다음과 같다.

- Web Agent의 상태 그래프 연구와 JavaScript profile 기반 최적화 연구를 더
  확인한다.
- Solid Connection에서 사용할 수 있는 작고 안전한 기능 흐름을 정한다.
- 행동별 상태와 chunk를 기록하는 수집기를 구현한다.
- 작은 실험으로 측정 가능성과 기존 기술 대비 차이가 있는지 확인한다.

작은 실험에서 차이가 확인되지 않으면 JavaScript 최적화까지 범위를 넓히지 않고
WebMCP가 Agent의 탐색 범위를 얼마나 개선하는지에 집중한다.

## 교수님 보고용 요약

교수님 안녕하십니까.

어제 윤제 학생과 연구 방향에 대해 이야기한 뒤 역할을 나누어 선행 연구를 찾아보고
있습니다. 윤제 학생은 CHI를 중심으로 브라우저 조작과 Web Agent 관련 연구를
조사하고 있고 저는 WebMCP와 WebMap 그리고 JavaScript 최적화 관련 연구를 보고
있습니다.

처음에는 WebMCP를 이용해 웹페이지의 상태와 행동을 WebMap으로 만드는 방향을
생각했습니다. 다만 비슷한 상태 그래프와 Agent 탐색 연구가 이미 있어 WebMap
자체만으로는 차이가 크지 않다고 판단했습니다.

그래서 현재는 WebMCP가 제공하는 행동의 의미와 실제 브라우저에서 실행된
JavaScript를 연결하는 방향을 보고 있습니다. Agent가 어떤 행동을 했을 때 화면이
어떻게 바뀌었고 어떤 JavaScript chunk와 함수가 사용됐는지를 함께 기록하는
방식입니다. 이후 방문에서는 예상되는 행동에 필요한 코드만 먼저 준비하고 다른
코드는 늦게 처리할 수 있는지도 확인해보려고 합니다.

아직 주제를 확정한 단계는 아니며 기존 V8 최적화나 비슷한 Agent 연구와 겹치는
부분을 더 확인하고 있습니다. 다음 주 초에 윤제 학생과 조사한 내용을 다시
정리한 뒤 실제로 비교할 수 있는 연구 질문과 작은 실험 범위를 정해보겠습니다.

감사합니다.
